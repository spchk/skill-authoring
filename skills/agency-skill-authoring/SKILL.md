# Навыки агентства: как создавать, упаковывать, публиковать

## When to Use

Триггеры: «сделай навык для команды», «оформим наш процесс как скилл», «хотим отдать инструмент наружу»,
«как упаковывается скилл», «что не должно попасть в публичный репозиторий», «внутренний или рыночный навык».
Не для этого навыка: чистка и аудит текущей библиотеки Hermes — там `skill-library-maintenance`.

Опирается на разбор репозиториев `ai-hub-open` (три публичных скилла по платному трафику, Apache-2.0),
сделанный 07.10.2026: `SKILL.md` + `references/` + `scripts/`, упаковщики `tools/build_skill_zip.py` и
`scripts/package_skill.py`, CI/release-workflow, CONTRIBUTING и шаблоны PR/issue.

## Три контура: куда попадает результат

| Контур | Где живёт | Кому доступен | Что обязательно |
|---|---|---|---|
| **Личный** | каталог навыков агента: `$HERMES_HOME/skills/<category>/<name>/` | только Антон и Hermes | SKILL.md + references/ + scripts/; ни версии, ни лицензии, ни README |
| **Внутренний** | уже существующий приватный репозиторий **`<org>/ai-skills`** (`skills/<name>/SKILL.md`), рабочая копия — `AI_SKILLS_REPO` (по умолчанию `~/projects/ai-skills`) + `install.sh` и/или tap | команда «Спичек» | LICENSE (внутренняя), README, CONTRIBUTING, CODEOWNERS, валидатор `tools/validate_skill.py` + CI, проверка на секреты и пути; `version` + `CHANGELOG.md` |
| **Внешний (рынок)** | публичный репозиторий `<concept>-skill`, MIT | все | README RU+EN, LICENSE MIT, `skills.sh.json`, репозиторный `install.sh`, CI, релизы по тегам, бренч `main`/`dev`, DCO; `version` + `CHANGELOG.md` + скрипт preflight |

По умолчанию начинай с **личного**: если навык обкатан только на одной задаче — публиковать нечего.

**Разделение с `hermes-skill-publishing`:** тот навык отвечает за доставку и витрину (каналы tap / skills.sh /
ClawHub, guard и `--force`, топология трёх репозиториев, лимиты GitHub Free, онбординг коллеги — в его
reference-файле `org-skill-library-distribution.md`). Этот навык — про то, что кладётся в репозиторий:
каркас SKILL.md, упаковка, валидация, релизная дисциплина. Не дублировать их содержимое здесь.

## Решение: внутренний или внешний

Три вопроса. **Любое «да» → сразу внешний контур**, не «сначала внутренний, потом решим»:

1. Методология не содержит наших клиентов — её можно показать чужому маркетологу без правок?
2. Инструмент решает задачу класса, а не только нашего клиента (ниша, площадка, тип процесса)?
3. Готовы держать это живым: отвечать на issues, выпускать версии, не ломать установленные копии без CHANGELOG?

Три «нет» — это внутренний навык, и это нормальный ответ: большинство наших процессов (работа с конкретным клиентом,
наша оргструктура, наши договоры) рынку не нужны и только создают обязательства.

## Каркас SKILL.md — единый для всех контуров

Порядок и назначение секций — в `references/skill-md-skeleton.md` (полный скелет с формулировками).
Коротко: H1 с названием роли → «Когда триггерится» → «Границы / чего скилл не делает» → «Что нужно от среды» →
«Главный принцип» → шаги воронки с артефактами и гейтами → «Как использовать references / scripts» →
«Стиль работы» → «Возобновление» → «При сбое шага».

Пять вещей, которые превращают набор инструкций в навык, а не в статью:

1. **«Что нужно от среды» — таблица способностей с веткой «если нет».** У каждой необязательной способности
   (MCP, запуск кода, чтение веб-страниц, субагенты) есть фолбек и строка «что теряется». Навык обязан дойти до
   конца без любой из них, а пропуск — печататься в артефакт шага, а не проглатываться.
2. **Артефакты между шагами.** Каждый шаг читает файлы предыдущих; если у шага нет входа — возврат на шаг-источник,
   а не догадка. Это то, что даёт возобновление работы через неделю.
3. **Гейты на побочных эффектах.** Всё, что пишет во внешнюю систему, тратит деньги, отправляет сообщение или
   публикует, делается черновиком / на паузе / после явного «ОК» человека. Удаление во внешней системе — никогда.
4. **Триггеры в description.** Description висит в промпте всегда, тело грузится по триггеру. Первые 57 знаков
   должны быть самодостаточным триггером, дальше — список фраз, по которым Антон реально это позовёт.
   Два разных лимита: у личного Hermes-навыка `skill_manage` **отклоняет описание длиннее 60 знаков** целой
   операцией, у публикуемого пакета лимит 200. Пиши сразу ≤60 — влезет везде, а остальные формулировки
   живут в теле, в разделе «Когда триггерится».
5. **«Стиль работы» и «Границы».** Императивные правила для агента (один вопрос за раз, артефакт в файл, сводка
   в чат) и явный перечень того, чего навык не делает — чтобы он не расширял задачу сам.

## Хранение в GitHub: репозиторий команды

Навыки команды живут в **уже существующем** приватном репозитории **`<org>/ai-skills`** — организация
`<org>`, рабочая копия — переменная `AI_SKILLS_REPO` (по умолчанию `~/projects/ai-skills`). Новый репозиторий под это создавать
не нужно: сначала `gh repo list <org>`. Личный профиль `<владелец>` для агентских репозиториев не используется.

Порядок движения навыка: пишется и обкатывается в библиотеке Hermes → переносится в рабочую копию →
валидатор → ветка → PR в `main` (ревьюер `@<ревьюер>` по CODEOWNERS, CI гоняет те же проверки).

```bash
python3 scripts/sync_skills.py status                        # что в репозитории и чем отличается от библиотеки
python3 scripts/sync_skills.py push <имя> --category <кат>    # перенести навык в рабочую копию + валидатор
python3 scripts/sync_skills.py check                         # валидатор репозитория по всем навыкам
```

`push` останавливается на секретах, серверных путях и кириллических именах файлов, добавляет `category`
во фронтматтер и печатает готовые команды ветки/коммита/PR. Коммит и push он не делает: в общий репозиторий
изменения уходят только через PR, и решение — за человеком.

Полный рунбук — раскладка репозитория, формат навыка, онбординг коллеги, состав команды, питфоллы —
в `references/internal-github-repo.md`.

## Версии, обновление и проверка требований

Навык живёт как продукт: у него есть версия, история и проверка того, что окружение готово к работе.
Три вещи обязательны в любом контуре, кроме личного:

1. **`version` в шапке `SKILL.md`** — единственный источник правды, и `CHANGELOG.md` рядом. Поднимать
   версию на смысловое изменение, в записи — «что делать с уже сделанным» (пересев, пересборка).
2. **Релиз** — тег `<имя-навыка>-v<версия>` и GitHub Release с текстом CHANGELOG: по нему навык
   сверяет себя с репозиторием (скрипт сверки версии в навыке, коды возврата `0/1/2`).
3. **Проверка требований до запуска** — не раздел «что нужно от среды», а скрипт проверки (preflight) в навыке:
   ключи (только маска!), живой пробный вызов моделей, баланс, наличие бинарников, оценка стоимости
   прогона. Блокер — то, без чего задача не будет сделана вообще; отсутствие отчёта или второго
   мнения — предупреждение. При блокере работу **не начинать**, а сказать владельцу.

Порядок «проверить требования → назвать цену → получить «да» → запускать» обязателен для всего, что
ходит в платные API, пишет в чужие системы или печатает файлы: массовые операции делаются по явному
согласию владельца, а не по умолчанию.

Полностью — `references/versioning-and-preflight.md`.

## Создание с нуля

```bash
# личный навык Hermes (контур 1)
python3 scripts/new_skill.py my-process --install-hermes knowledge
# навык команды: папка в рабочей копии <org>/ai-skills, дальше — валидатор и PR в main (контур 2)
python3 scripts/new_skill.py audit-cabinet --mode internal --category knowledge
# навык для рынка: отдельный публичный репозиторий (контур 3)
python3 scripts/new_skill.py ad-audit --mode external --repo-name ad-audit-skill --dir ~/projects
```

Скрипт проверяет имя и длину описания и раскладывает каркас: `SKILL.md` по канону, `references/`, `scripts/`.
В режиме `internal` он работает внутри существующего репозитория агентства — создаёт только папку навыка
`skills/<name>/` с фронтматтером `name`/`description`/`category` и печатает шаги ветки и PR; никаких
`git init` и новых репозиториев. Режим `external` дополнительно кладёт README, LICENSE MTI, `skills.sh.json`,
репозиторный `install.sh`, CI и релиз-воркфлоу, `tools/package_skill.py` и CHANGELOG.

Образцы наших уже опубликованных репозиториев: `<владелец>/gdebenz-skill`, `<владелец>/vk-video-skill`
(MIT, README RU+EN, `skills.sh.json`, `install.sh`, `skills/<name>/`).

## Упаковка

```bash
python3 scripts/package_skill.py --check                          # только валидация
python3 scripts/package_skill.py                                  # собрать <name>.zip в dist/
python3 scripts/package_skill.py --target claude                   # жёсткие правила портируемости (для рынка)
python3 scripts/package_skill.py --target hermes --public-check    # чек-лист перед публикацией наружу
```

Что проверяется и почему именно так — `references/packaging-and-validation.md`. Главное:
**упаковщик останавливается на секретах**, а не молча их выкидывает: `.skill` рассылается коллегам и клиентам,
`.gitignore` от этого не защищает. Перед внешней публикацией — `--public-check`: внутренние пути, имена
клиентов, id кабинетов.

## Публикация на рынок

Маршрут целиком — `references/external-release-playbook.md`: лицензия и её обязательства, раскладка репозитория,
ветки `main`/`dev`, правила PR и DCO, релизные заметки для пользователей (не технический CHANGELOG), CI и релиз
по тегу, что не должно попасть в публичную историю и почему отзыв ключа важнее чистки истории.
Каналы доставки и витрина (tap, skills.sh, ClawHub, guard) — в скилле `hermes-skill-publishing`.

## Потребление чужих навыков (обратный поток)

Ставим чужой навык в Hermes → все правки делаем **в оверлеях**, а не в live-папке: обновление затирает папку
целиком. Механика — скилл `skill-library-maintenance`, раздел про апстрим-апдейты, и папка
`<папка оверлеев агента>` в проектной папке Hermes.

## Проверка перед сдачей

```bash
python3 scripts/package_skill.py --skill-path <папка навыка> --check
```

Навык считается готовым, когда: упаковщик чист; `install.sh` разложил навык в каталог агента (проверь на
пустом каталоге через `--dir`); каждое утверждение о лимитах/ценах имеет источник и дату; в SKILL.md нет
«UPDATE: на самом деле…»; секретов нет ни в навыке, ни в истории репозитория.

## Питфоллы

- **Перед созданием репозитория — посмотреть, что уже есть.** `gh repo list <org>`. Рабочие репозитории
  агентства живут в организации `<org>`, репозиторий навыков там уже есть (`ai-skills`); создание
  дубликата в личном профиле — это два расходящихся источника правды и лишняя уборка.
- **Не публиковать наш контекст по инерции.** Серверные пути, имена клиентов, id кабинетов (`<ID кабинета>`),
  суммы и выгрузки — это то, что утекает первым при копировании внутреннего файла в публичный README.
- **description — не аннотация, а триггер.** «Помогает с рекламой» не вызовется никогда; «Use when таблица
  согласования Директа или VK с клиентом» вызывается. Лимиты: ≤60 знаков у личного Hermes-навыка
  (ограничение записи, не советы), ≤200 у публикуемого пакета, 1024 по спеке — но длинное описание не помогает
  маршрутизации, а ломает совместимость.
- **Одна точка правды.** Не дублировать фактуру в чужие навыки: описание процесса живёт в своём навыке,
  а в соседнем — максимум строка-указатель.
- **Лицензия — MIT по умолчанию.** Так выпущены наши публичные репозитории; Apache-2.0 берём, только если
  внутрь попал Apache-код или нужна патентная оговорка. Копируя чужой код, сохраняй его LICENSE и атрибуцию,
  а свой публичный навык выпускаем под своим названием: чужие имена и бренд в публичном продукте — претензии.
- **Публичный репозиторий = обязательство.** Ветка `main` защищена, изменения через PR, а релиз — это PR из `dev`
  обычным merge-коммитом (squash ломает сверку веток). Не готов держать — значит внутренний контур.
- **Пакет должен ставиться без кода.** «Распакуй архив → положи папку в каталог скиллов агента → перезапусти
  сессию» (а если у навыка есть зависимости — ещё `python install.py`). Наши репозиторные каркасы дают для
  этого `install.sh --agent …` и установку через tap. Если для установки нужен клон, git или ручная правка
  конфигов — половина людей не установит.
- **Секрет в публичной истории считается скомпрометированным в момент публикации** — отзывать ключ, а не
  переписывать историю: переписывание ломает форки и клоны, а факт утечки уже состоялся.

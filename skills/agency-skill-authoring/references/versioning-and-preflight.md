# Версии навыков, проверка обновлений и требований

Навык, который установили себе коллеги или чужие люди, живёт без нас. Поэтому у него есть версия,
история изменений и **скрипт проверки требований**: агент обязан выяснить, что окружение готово, до
работы, а не посреди прогона.

Этот файл — продолжение `skill-md-skeleton.md`: там каркас текста, здесь механика версий и проверок.

## Три вещи, которые делают навык обновляемым

| Что | Где живёт | Кто читает |
|---|---|---|
| Версия | шапка `SKILL.md`: `version: 1.2.0` | агент и человек, глазами |
| История изменений | `CHANGELOG.md` рядом с `SKILL.md` | человек перед обновлением |
| Точка сверки в GitHub | тег `<имя-навыка>-v<версия>` + Release | скрипт `check_update.py` |

Версия — **единственный источник правды**. Не дублировать её в README (разъедется): README описывает
навык, версия живёт в одном месте.

### Когда поднимать версию

- **minor** (`1.1.0 → 1.2.0`) — смысловое изменение: новая секция, другой кодбук, другой формат
  вывода, новые требования к среде. Всё, после чего старая инструкция у агента даст не тот результат.
- **patch** (`1.1.0 → 1.1.1`) — правки, которые ничего не меняют в поведении: опечатки, ссылки,
  формулировки, обновлённый факт с датой проверки.
- **major** (`1.1.0 → 2.0.0`) — несовместимость: поменялся формат артефакта, и уже сделанная работа
  по старой версии не стыкуется с новой.

Правило про артефакты: если версия выросла и это меняет **формат данных** (JSONL, схему кодбука,
имена файлов), в CHANGELOG обязательна строка «что делать с уже собранным»: пересев, пересборка
агрегатов, чем сравнивать старые и новые цифры. Два разных формата в одном корпусе смешивать нельзя,
и узнать об этом человек должен из CHANGELOG, а не из испорченного отчёта.

### CHANGELOG

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), сверху свежее:

```markdown
## [1.2.0] — 2026-10-09

Добавлено:
- проверка доступности моделей перед прогоном (`scripts/preflight.py`);

Изменено:
- кодбук отеля: подкоды закрыты словарём, предложения выносятся отдельным блоком.

Миграция: корпуса, размеченные версией ≤ 1.1.0, пересеять — подкоды нормализованы.
```

## Релиз

```bash
git tag -a <имя-навыка>-v1.2.0 -m "<имя-навыка> 1.2.0"
git push origin <имя-навыка>-v1.2.0
gh release create <имя-навыка>-v1.2.0 --title "<имя-навыка> 1.2.0" --notes-file skills/<имя-навыка>/CHANGELOG.md
```

- один тег на навык: в репозитории с несколькими навыками релизы не мешают друг другу;
- заметки релиза — не технический CHANGELOG, а «что теперь по-другому у того, кто этим пользуется»;
- `--latest` не ставить вручную в мультинавычном репозитории: GitHub выберет сам.

## Проверка обновления у потребителя

В навык кладётся `scripts/check_update.py` (рабочая реализация — в наших навыках, файл
`scripts/check_update.py` внутри навыка): скрипт читает `version` из своей шапки,
спрашивает последний подходящий релиз через `gh api` (или GitHub API с `GITHUB_TOKEN`) и печатает
статус: `актуально` / `есть обновление` / `локальная новее` / `нет релизов` / `не проверить`.

Вызывать: перед каждым новым проектом и перед сменой схемы разметки. Коды возврата: `0` — ок,
`1` — есть обновление (можно вешать в cron с алертом), `2` — проверить не удалось.

Как реагировать:

- **есть обновление** → сказать владельцу, что нового (по CHANGELOG), чем это важно для текущей
  работы, и обновить: `hermes skills update`, либо `git pull` в клоне + `./scripts/install.sh --apply --force`;
- **локальная новее** → правки не выложены: закоммитить, поднять версию, выпустить релиз. Иначе у
  команды и у агентов будет старая схема, а расхождение обнаружится на клиентском корпусе;
- **не проверить** (нет `gh`, нет доступа к приватному репозиторию) — сказать прямо, а не делать
  вид, что версия актуальна.

## Требования к среде: проверять до запуска, а не во время

В навыке есть раздел «Что нужно от среды», но раздел — это обещание, а не проверка. Для навыков,
которые ходят в модели, платят за API, пишут в чужие системы или печатают файлы, кладём рядом
скрипт проверки (в наших навыках — `scripts/preflight.py`).

Что проверяет такой скрипт:

1. **Базовое окружение** — версия Python, обязательные модули, наличие бинарников (браузер для PDF,
   `gh` для релизов). Отсутствие необязательного — предупреждение с пометкой «что теряется».
2. **Ключи** — из окружения, иначе из файла (`$HERMES_ENV_FILE` → `~/.env` → `./.env` → вверх по
   дереву). Печатать **только маску**: `sk-15f…f752`. Никогда не выводить значение и не коммитить.
3. **Живая работоспособность, а не наличие ключа.** Ключ может быть жив, а модель переименована,
   баланс пуст, доступ отозван. Поэтому — пробный вызов на 1 токен и запрос баланса/лимитов.
   Это стоит доли копейки и снимает целый класс сюрпризов на середине прогона.
4. **Оценка стоимости** по замеренным ставкам — таблицей, для 2–3 типичных объёмов работы. Владелец
   должен увидеть цену до «да», а не после счёта.
5. **Итог с кодом возврата**: `0` — можно запускать, `1` — есть блокер. Кто работает по этому
   навыку, обязан прогнать проверку первым шагом и **при блокере не начинать** работу, а сказать
   владельцу: нет ключа, нет баланса, модель не отвечает.

Разделение на блокеры и предупреждения задаётся так: блокер — то, без чего задача не будет сделана
вообще (нет доступа к источнику данных, нет модели разметки); предупреждение — то, что сужает выдачу
(нет отчёта, нет дашборда, нет второго мнения).

Правило про модели: **дешёвая модель для массовой работы, сильная — для текста и валидации**.
Проверять обе, а не только ту, которую выбрали: смена модели на дешёвую без замера — это риск
качества, а смена на дорогую — риск бюджета. Замер: 20–50 объектов на новой модели + сверка с
эталоном, и только потом прогон.

Порядок «проверить → назвать цену → получить да → запустить» — часть навыка, а не вежливость:
массовые прогоны и обращения к платным API делаются по явному согласию владельца.

# Внешний релиз: как выкладывать навык агентства на рынок

Чек-лист и порядок. Собрано из практики `ai-hub-open` (CONTRIBUTING, шаблоны PR/issue, CI, release-workflow)
и наших опубликованных репозиториев (`gdebenz-skill`, `vk-video-skill`). Каналы доставки, витрина
и guard живут в навыке `hermes-skill-publishing` — здесь только про репозиторий и релиз.

## 0. Проверка на входе

Навык уже живёт внутри и обкатан на 2–3 задачах; в текстах нет клиентов, кабинетов, сумм и внутренних
путей (прогон `package_skill.py --target claude --public-check --strict-public --check`); есть кому
отвечать на issues.

## 1. Лицензия и права

- Наш публичный навык — **MIT** (так выпущены `gdebenz-skill` и `vk-video-skill`): можно использовать,
  править и встраивать, требуется сохранить копирайт и текст лицензии. `new_skill.py --mode external`
  кладёт готовый `LICENSE` с `Copyright (c) <год> Антон Белицкий`.
- **Apache-2.0** берём, если внутрь попал Apache-код или нужна явная патентная оговорка; тогда в копии
  должны остаться `LICENSE`/`NOTICE` оригинала.
- Чужой код: сохраняем лицензию и пишем в README «Adapted from <repo> (<лицензия> © автор)».
- Название и бренд — свои. Чужие имена навыков и репозиториев в публичном продукте — источник претензий.

## 2. Раскладка репозитория (наш паттерн)

```
<concept>-skill/
├── README.md              RU, полный: возможности, установка, требования, границы, лицензия, ключевые слова
├── README.en.md           EN, сокращённый
├── LICENSE                MIT
├── skills.sh.json         groupings для страницы на skills.sh
├── CHANGELOG.md           semver; релизные заметки — в docs/releases/
├── skills/                FLAT: один уровень, skills/<name>/SKILL.md (так читает Hermes tap)
│   └── <name>/  SKILL.md + references/ + scripts/
├── scripts/install.sh     --agent hermes|openclaw|claude|cline|codex|cursor, автоопределение
├── tools/package_skill.py упаковщик (в пакет не попадёт)
├── docs/releases/         заметки для пользователей по тегам
└── .github/workflows/     ci.yml + release.yml
```

Вложенные категории (`skills/<category>/<name>/`) не годятся: tap обходит ровно один уровень и категория
выглядит скиллом без SKILL.md. Категории выражаются `skills.sh.json` и frontmatter.
Имя репозитория — `<concept>-skill`; несколько навыков в одном репо — норма (тогда CI и релиз идут циклом).

## 3. README — что должно быть (правило: чужому человеку понятно без вопросов)

Возможности → Быстрый старт с примером вывода → Установка по агентам (Hermes tap, `npx skills add`,
`install.sh`, вручную) → Требования (где взять ключ, ключи — вне репозитория) → Что на выходе (артефакты) →
Важно знать (границы и известные ограничения) → Лицензия → Ключевые слова RU+EN.

Установка должна работать без кода: `install.sh` с автопределением агента и `--dir PATH`. Если нужен
клоны, ручная правка конфигов или сборка — половина людей не поставит.

## 4. Ветки и PR

- Две постоянные ветки: `main` (то, что ставят себе) и `dev` (рабочая).
- Ветка под задачу — **от `dev`**; PR — **в `dev`**. GitHub подставляет `main` по умолчанию: базу переключить,
  иначе PR переоткрывать.
- `main` защищена: прямой push отклоняется у всех, force-push запрещён (на публичном репо это доступно на Free).
- Релиз — PR из `dev` в `main` **обычным merge-коммитом**: squash меняет хеши, ветки расходятся, следующий PR
  тянет чужие изменения и конфликты. После слияния `dev` не удалять и подтянуть `main` обратно в `dev`.
- Имена ветвей по смыслу: `feat/lookalike-audiences`, `fix/pdf-cyrillic`, `docs/install-macos`.
- Коммиты — с DCO: `git commit -s` (строка `Signed-off-by:`), отдельного договора не нужно.

## 5. Шаблон PR и issues

PR: что меняет; зачем (ссылка на issue); чек-лист — база `dev`, ветка от `dev`, нет ключей/`.env`/внутренних
ссылок/данных клиентов, коммиты подписаны, документация и раздел об ограничениях обновлены, правила
безопасности не ослаблены, имена полей сверены с документацией площадки.

Issues: bug (что делал / что ожидал / что вышло / версия) и proposal (что предлагаю; какую задачу решает;
как решаю сейчас; есть ли это в API площадки — со ссылкой).

## 6. Релизы

1. Запись в `CHANGELOG.md` (`## X.Y.Z — YYYY-MM-DD`).
2. Релизные заметки для пользователей — `docs/releases/vX.Y.Z.md` («что изменилось для вас» + как обновить).
3. Merge `dev` → `main`, тег `vX.Y.Z`; воркфлоу собирает пакеты и прикрепляет архивы к релизу — это
   единственный способ получить архив без суффикса `-main` из кнопки GitHub Download ZIP.
4. Ломающие изменения — только мажорной версией и с явной инструкцией миграции.
5. После релиза — проверить, что raw-файлы отдаются (200) и что страница на skills.sh/индекс обновились;
   бейдж и топики репозитория выставляются сразу, индексация может занять день-два.

## 7. Что не должно попасть в публичную историю

- Ключи и токены, включая «отозванные» и «тестовые»: `.env`, `credentials.json`, `*.pem`, `*.key`, `id_rsa`.
- Внутренние адреса: ссылки на наши трекеры, серверные пути (`/opt/…`), хосты `*.beget.tech`.
- Данные клиентов: выгрузки статистики, id кабинетов (`<орг>-<цифры>-<слаг>`), CRM-списки, переписка, имена.
- Скриншоты личных кабинетов с логинами и цифрами клиента.

Ключ, попавший в публичный коммит, считается скомпрометированным с момента публикации: переписывание истории
ломает форки и клоны, а утечка уже состоялась. Действие номер один — отозвать ключ у сервиса.

## 8. Что даёт внешний контур (чтобы не делать это зря)

- Внешняя валидация методологии: чужие маркетологи приходят с багами и кейсами, которых мы не видели.
- Витрина работает как посадочная: README и реестры дают трафик на услуги агентства.
- Дистрибуция чужой рукой: коллеги ставят навык себе сами, а не мы его навязываем.

Цена: обязательства по issues и версиям и запрет на «потом прикрутим» публикацию клиентских данных.

# Хранение навыков в GitHub: репозиторий агентства

Рабочий рунбук по внутреннему контуру. Проверено на живом репозитории
**https://github.com/<org>/ai-skills** — приватный, в организации `<org>`, ветка `main`.

## Главное правило: только организация

**Рабочие репозитории агентства живут в организации `<org>`, не в личном профиле `<владелец>`.**
Личный профиль — для личных проектов. Перед тем как что-то создавать, сначала посмотреть, что уже
есть: `gh repo list <org>`. Репозиторий навыков там уже есть, и новый создавать не нужно.

## Зачем вообще репозиторий

Навык в каталоге навыков агента (`$HERMES_HOME/skills/`) живёт только у Антона. Чтобы процесс работал у команды, навык должен
приезжать на машину коллеги — а для этого нужен источник, из которого его можно поставить
и обновить. Git — самый дешёвый такой источник: доступ по участникам, история, ревью.

1. **Одна точка правды.** Коллега ставит навык из репо, а не копирует у соседа по чату.
2. **Обновление вместо размножения копий.** `git pull` + `install.sh` — и у человека свежая версия.
3. **Ревью и история.** Видно, кто и зачем поменял процесс; откат — `git revert`, а не воспоминания.

## Что уже лежит в репозитории (не изобретать заново)

```
ai-skills/
├── README.md                 что это, как поставить, чего здесь быть не должно
├── CONTRIBUTING.md           формат навыка, чек-лист, порядок PR, что не принимаем
├── LICENSE                   внутренний ресурс, вне команды не распространяется
├── CODEOWNERS                ревьюер по всем путям — @<ревьюер>
├── scripts/install.sh        ставит навыки в каталог агента (--apply, --force, --agent, --dir)
├── tools/validate_skill.py   проверка навыков по правилам репозитория
├── .github/workflows/ci.yml  CI на PR в main: валидатор + синтаксис + секреты в индексе
└── skills/                   FLAT: один уровень, skills/<имя>/SKILL.md (+ references/, scripts/)
```

Вложенных категорий (`skills/<категория>/<имя>/`) здесь нет и быть не должно: Hermes обходит
`skills/` ровно на один уровень, категория указывается полем `category` во фронтматтере.

## Формат навыка в этом репозитории

```yaml
---
name: имя-навыка            # = имя папки, строчная латиница через дефис
description: "Use when …"   # ≤60 знаков, начинается с триггера, заканчивается точкой
category: knowledge         # productivity | knowledge | api-integration | ...
---
```

Проверяется автоматически: `python3 tools/validate_skill.py` (все навыки) или
`python3 tools/validate_skill.py skills/<имя>` (один). Что проверяет:

- имя папки = `name`, латиница через дефис;
- `description` не длиннее 60 знаков, начинается с «Use when», заканчивается точкой, без XML-тегов;
- обязательные поля фронтматтера `name`, `description`, `category`;
- ровно один `SKILL.md` на навык, лежит в корне навыка;
- все ссылки вида `references/…` и `scripts/…` из `SKILL.md` существуют;
- нет файлов с секретами (`.env`, `credentials.json`, `*.pem`, `*.key`, `id_rsa`) и секретных
  строк (OpenAI/Anthropic `sk-…`, Яндекс `y0_…`, Yandex Cloud `AQVN…`, Replicate `r8_…`,
  GitHub `ghp_…`, Google `AIza…`, приватные ключи);
- нет серверных абсолютных путей (`/opt/…`) — у коллег этих путей нет;
- нет байт-кода и артефактов сборки.

Тот же валидатор гоняет CI на PR, поэтому локальный прогон до пуша = зелёный CI.

## Цикл работы

```bash
# локальная рабочая копия
cd "${AI_SKILLS_REPO:-$HOME/projects/ai-skills}" && git pull

# 1. ветка от main
git checkout -b add-<имя-навыка> main
# 2. навык: писать и обкатывать в каталоге навыков агента (<HERMES_HOME>/skills/<категория>/<имя>/), затем перенести содержимое
#    в skills/<имя>/ (только SKILL.md, references/, scripts/, assets/, templates/)
# 3. проверка
python3 tools/validate_skill.py skills/<имя-навыка>
# 4. коммит и PR в main
git add -A && git commit -m "Навык <имя>: что он делает"
git push -u origin add-<имя-навыка>
gh pr create --repo <org>/ai-skills --base main --head add-<имя-навыка> --title "…" --body "…"
```

`main` не пушим напрямую: в репозитории один хозяин-ревьюер (`@<ревьюер>` по CODEOWNERS), а истории
изменений навыков команда доверяет. Технического запрета нет — на GitHub Free защита ветвей у
приватных репозиториев недоступна, это договорённость, зафиксированная в CONTRIBUTING.

**Питфолл авторства.** PR, созданный из-под аккаунта Антона (а токен Hermes — его), GitHub считает
его собственным: запросить ревью у `@<ревьюер>` не даст (`Review cannot be requested from pull request
author`). Такие PR Антон смотрит и мержит сам; коллеги — через свои аккаунты.

**Питфолл имён файлов.** Имена справочников — латиницей (`example-task-reconciliation.md`, а не
`пример-задачи….md`): так их одинаково видят все агенты и не ломаются ссылки при копировании.

## Портируемость путей

Абсолютные пути нашего сервера на машине коллеги не работают — валидатор их не пропустит.
Два законных решения: убрать путь из текста (обычно он там не нужен) или заменить на относительный
(`~/projects/…`). Кириллические имена файлов — тоже замена, см. выше.

## Онбординг коллеги (первый раз, 5 минут)

1. `gh auth login` — у коллеги должен быть доступ к организации `<org>` (иначе приватный репо не клонируется).
2. `git clone https://github.com/<org>/ai-skills.git && cd ai-skills`
3. `./scripts/install.sh` — покажет план; `./scripts/install.sh --apply` — поставит навыки в каталог агента
   (`--agent hermes|claude|cline|codex|openclaw|cursor`, `--dir` для нестандартного пути).
4. Перезапустить сессию агента.

Альтернатива для Hermes — tap:

```bash
hermes skills tap add <org>/ai-skills
hermes skills check
hermes skills install <имя-навыка> --force
```

`--force` нужен не из-за поломки: источник уровня `community`, и guard просит подтверждение. Так
устроена политика для любого репозитория вне списка доверенных (там только вендоры).

## Обновление у команды

```bash
hermes skills check && hermes skills update <имя>            # через tap
git -C ai-skills pull && ./ai-skills/scripts/install.sh --apply   # через клон
```

`install.sh` перезаписывает папку навыка целиком. Это правильно: правки живут в репозитории, а если
коллега починил что-то локально — он присылает PR, иначе правка умрёт при первом обновлении.

## Состав команды и доступ

Состав команды: владелец и разработчики; доступ выдаётся приглашением в организацию.
Доступ выдаётся по репозиторию, а не по папке: кому нужен только один навык — тому нужен отдельный
приватный репозиторий под него, а не папка внутри общего.

## Питфоллы

- **Приватный репозиторий не индексируется skills.sh** — публичной витрины не будет, и это нормально
  для внутреннего контура.
- **Branch protection на бесплатном плане** для приватных репозиториев недоступна: «в main только
  через PR» держится CONTRIBUTING и код-овнером, а не настройками GitHub.
- **Личные навыки — не сюда.** Репозиторий читают все участники, включая добавленных позже.
  «Папка для личного внутри командного репо» — это не приватность, а её видимость.
- **Клиентские данные.** Репозиторий приватный, но это не отменяет правила: ID объектов ПланФикса и
  карты кабинетов допустимы как рабочий справочник, персональные данные клиентов, токены и
  коммерческие условия сделок — нет.
- **Обновление у коллеги не мгновенное.** Пока он не сделал `pull` + `install.sh`, у него старая
  версия: для важных правок пишите в чат команды «обнови навыки».
- **Не создавать навык сразу в репозитории.** Писать и обкатывать — в библиотеке Hermes, в репозиторий
  уезжает уже работающая версия (см. `packaging-and-validation.md`).
